# 技术说明

## 一、模块结构

```
minimax/
├── sddctx/                     上下文模块
│   ├── config.py               配置：环境文件 → Settings
│   ├── material_store.py       seekdb 存取：工程资料的表、导入、检索
│   ├── importer.py             把工作负载目录里的规格/代码/测试读成可入库的条目
│   ├── context_builder.py      检索结果 → 上下文包（摘要 + 提示词渲染）
│   ├── state_store.py          PowerContext 存取：任务状态的读写
│   ├── minimax_client.py       MiniMax 对话补全客户端
│   ├── patch_apply.py          补丁校验与落盘
│   └── cli.py                  命令行入口
├── scripts/                    启动、测试、验证、技术记录脚本
├── workload/                   业务工程与本次开发的物料
│   ├── specs/                  规格条目
│   ├── app/                    业务工程 linewindow
│   └── snapshots/              修改前后的代码快照、规格各版本
└── logs/                       测试日志与技术使用记录
```

## 二、上下文是怎么选出来的

四步，全部在 `context` 子命令里完成。

1. **导入**：`importer.py` 扫描 `minimax/workload`，把 `specs/*.md`、
   `app/**/tests/*.py` 之外的 `app/**/*.py` 分别读成三类条目。条目里带
   `revision`（文件里 `revision: <n>` 头声明）和 `source`（相对路径）。
2. **入库**：`material_store.py` 把三类条目分别写进 seekdb 的 `sdd_spec`、
   `sdd_code`、`sdd_test`，主键是条目编号，重新导入用新版本覆盖旧版本。
3. **检索**：用任务关键词对三张表做一次 `LIKE` 匹配（`search`），三表
   `UNION ALL` 后按类别和编号排序返回。
4. **组装**：返回的行按类别分成规格、代码、测试三组，每组内部按「命中关键词
   次数降序、编号升序」排序后取前 N 条。规格、代码、测试都带上来源路径与版本号，
   连同从 PowerContext 读回的任务进展一起组成 `ContextPackage`。
   `ContextPackage.digest` 是这三组「编号 + 版本」的 sha256 摘要，用来判断上下文
   是否变化。

选择依据是任务关键词与资料正文的匹配，不依赖人工挑选。规格更新后重新导入，
下一次检索读到的是新版本，返回的正文与摘要都会变（见 `minimax/logs/spec_change.log`）。

## 三、三项技术的分工

| 技术 | 承担 | 代码位置 | 证据 |
| --- | --- | --- | --- |
| **seekdb** | 存规格、代码、测试三类工程资料；检索结果用于构造上下文 | `material_store.py`、`importer.py` | `logs/seekdb_queries.log` |
| **MiniMax** | 依据上下文产出代码修改 | `minimax_client.py` | `logs/minimax_call.json`、`logs/minimax_patch.diff` |
| **PowerContext** | 保存任务进展与验证结果；重启后读回并用于后续上下文 | `state_store.py` | `logs/powercontext_state.log` |

三者串成一条链：seekdb 提供「改什么」的依据 → MiniMax 产出补丁 → PowerContext
记录「做到哪一步」，下次运行从记录处继续。

## 四、模块的输入与输出

入口是命令行 `python -m sddctx`。每个子命令的输入输出见
`minimax/README.md` 第四节。核心产出是 `context` 子命令的 JSON：

```json
{
  "task_id": "sdd-task-001",
  "objective": "...",
  "digest": "e5fabcf1dfbc6931",
  "specifications": [{"id": "...", "revision": 1, "source": "...", "body": "..."}],
  "code": [{"id": "...", "revision": 1, "source": "...", "body": "..."}],
  "tests": [{"id": "...", "revision": 1, "source": "...", "body": "..."}],
  "state": {"completed": [...], "todo": [...], "verification": [...]}
}
```

`--prompt` 会额外附上渲染好的提示词全文，那就是交给 MiniMax 的那份输入。

## 五、本次开发

业务工程 `linewindow` 的 `read_range` 在读取范围超出内容长度时静默截断，不留任何
标记。规格 `SPEC-001` 要求截断时报告 `source_range_clamped`，同时保持其余七条
行为不变。

改动一个文件，四处修改，见 `minimax/技术使用记录.md` 1.4 节的对应表。改动前后
同一组目标功能测试从「6 失败」变为「12 通过」，回归测试 22 条始终通过。
