# 验证样例

本文件按步骤说明如何验证本作品。评审从干净环境开始，按第五节的顺序执行即可。

## 一、任务描述

**任务编号**：`sdd-task-001`

**业务工程**：`linewindow`，一个读取文本文件行区间的 Python 库，位于
`minimax/workload/app/`。它有两个模块：

- `linewindow/reader.py`：按行区间读取内容，返回内容、起止行号和一组限制标记。
- `linewindow/indexer.py`：用 AST 索引源文件里的顶层函数与类。

**要改什么**：当读取请求的 `end` 大于内容实际拥有的行数时，函数原本静默地把读取
范围截断到内容末尾，既不报错也不留下任何标记。调用方无法区分「内容本身只有这么多
行」和「我请求的范围被截断了」。修改后必须在 `limitations` 中报告
`source_range_clamped`。

**哪些原有行为必须保持**（逐条列在规格里，也逐条有测试守着）：

1. `start` 超过内容实际行数时，仍然抛出 `RangeError`，`code` 为 `code_range_missing`。
2. `start` 不超过内容实际行数时，读取到的内容与修改前完全一致。
3. 请求范围完全落在内容之内时，不加入 `source_range_clamped`。
4. 请求的 `end` 恰好等于实际行数时，不加入 `source_range_clamped`。
5. 因为单行内容过长而截断内容时，仍然使用既有的 `source_truncated` 标记。
6. 因为单行内容过长而无法返回任何内容时，仍然使用既有的 `source_line_too_large` 标记。
7. `source_range_clamped` 与 `source_truncated` 可以同时出现。

## 二、有效规格

规格文件：`minimax/workload/specs/SPEC-001-read-range-clamp.md`

规格的第一行是标题，第二行之后有 `revision: <n>` 头。版本号随资料一起存在 seekdb
里，重新导入时用新版本覆盖旧版本。

规格内容可以在上下文输出里直接看到（`specifications[].body`），也可以用
`minimax/logs/development_prompt.md` 查看模块渲染进提示词的那一份。

## 三、初始数据

导入前 seekdb 是空的。执行 `init` 之后：

| 表 | 内容 | 条数 |
| --- | --- | --- |
| `sdd_spec` | `SPEC-001-read-range-clamp` | 1 |
| `sdd_code` | `app/linewindow/reader.py`、`app/linewindow/__init__.py`、`app/linewindow/__main__.py`、`app/linewindow/indexer.py` | 4 |
| `sdd_test` | `app/tests/test_reader_range_clamp.py`、`app/tests/test_reader.py`、`app/tests/test_indexer.py` | 3 |

PowerContext 侧初始为空。任务状态在第一次 `state save` 之后才存在，Scope 由模块
按 `idempotency_key` 自动创建。

## 四、上下文必须包含的内容

执行 `context` 之后，输出必须能定位到下面四类信息：

| 要求 | 在输出里的位置 | 本次结果 |
| --- | --- | --- |
| 本次任务适用的规格条目 | `specifications[]` | `SPEC-001-read-range-clamp`，revision 1，来源 `specs/SPEC-001-read-range-clamp.md` |
| 需要修改的代码文件或符号 | `code[]` | `app/linewindow/reader.py`（含 `read_range`）、`app/linewindow/__init__.py`、`app/linewindow/__main__.py`、`app/linewindow/indexer.py` |
| 用于验证功能及兼容性的测试 | `tests[]` | `app/tests/test_reader_range_clamp.py`（新增功能）、`app/tests/test_reader.py`、`app/tests/test_indexer.py`（兼容性） |
| 已完成事项、待办事项、已有验证结果 | `state` | 从 PowerContext 读回的 `completed` / `todo` / `verification` |

每一条都带 `source` 字段，指向仓库里的真实路径。

## 五、操作步骤与预期结果

### 步骤 0：准备

```bash
docker run -d --name seekdb-ctx -p 2881:2881 -e TZ=Asia/Shanghai oceanbase/seekdb:latest
python -m pip install pymysql httpx pytest
```

### 步骤 1：启动 PowerContext Server

```bash
python minimax/scripts/start_server.py run --env-file minimax/powercontext.env
```

**预期**：`/health/ready` 返回 `{"status":"ready", ...}`。

### 步骤 2：初始化数据

```bash
PYTHONPATH=minimax python -m sddctx init --reset --env-file minimax/sddctx.env
```

**预期**：`imported` 与 `stored` 都是 `{"code": 4, "specifications": 1, "tests": 3}`。

### 步骤 3：确认数据库里真的有资料

```bash
python minimax/scripts/record_seekdb.py
```

**预期**：`minimax/logs/seekdb_queries.log` 里列出四张表、各类行数、检索语句原文，
以及检索返回的 8 行（含 `spec` 1 行、`code` 4 行、`test` 3 行）。

### 步骤 4：组装上下文

```bash
PYTHONPATH=minimax python -m sddctx context --env-file minimax/sddctx.env \
  --task-id sdd-task-001 \
  --objective "Implement SPEC-001: report a clamped line range when the requested end exceeds the content length" \
  --keyword read_range --keyword source_range_clamped --keyword clamp --keyword limitations \
  --limit 5 --prompt
```

**预期**：第四节表格里的四类内容全部出现，每条都带真实来源路径。

### 步骤 5：保存任务状态

```bash
PYTHONPATH=minimax python -m sddctx state save --env-file minimax/sddctx.env \
  --task-id sdd-task-001 \
  --objective "Implement SPEC-001: report a clamped line range when the requested end exceeds the content length" \
  --completed "Imported the specification, the code and the tests into seekdb" \
  --todo "Produce the patch with MiniMax" \
  --verification '{"name":"target_tests_before","result":"6 failed, exit code 1"}'
```

**预期**：返回 `saved: true` 和一个 `scope_id`。

### 步骤 6：重启模块后读取并使用状态

停掉 PowerContext Server 再启动，然后：

```bash
PYTHONPATH=minimax python -m sddctx state show --env-file minimax/sddctx.env --task-id sdd-task-001
```

**预期**：返回步骤 5 写入的内容，Scope 编号不变。

再执行一次步骤 4 的 `context`：

**预期**：输出的 `state` 字段非空，且渲染出的提示词（`--prompt`）里出现
`## Progress recorded earlier` 段落和 `- [done]` / `- [open]` 条目。

### 步骤 7：记录改动前的失败

```bash
python minimax/scripts/reset_workload.py --state before
python minimax/scripts/run_tests.py target-before
```

**预期**：退出码 1。失败的 6 条都是断言 `source_range_clamped` 出现在
`limitations` 里，日志 `minimax/logs/target-before.log` 里能看到完整断言与实际值。

### 步骤 8：让 MiniMax 产出补丁并应用

有 `MINIMAX_API_KEY` 时：

```bash
PYTHONPATH=minimax python -m sddctx patch --env-file minimax/sddctx.env \
  --task-id sdd-task-001 \
  --objective "Implement SPEC-001: report a clamped line range when the requested end exceeds the content length" \
  --keyword read_range --keyword source_range_clamped --keyword clamp --keyword limitations \
  --output minimax/logs/minimax_patch.diff
```

没有 Key 时，直接用本次已经产出的补丁
`minimax/logs/minimax_patch.diff`（它由 MiniMax 依据同一份上下文和同一份提示词
产出，开发记录见 `minimax/logs/minimax_call.json` 与
`minimax/技术使用记录.md`）。

应用补丁：

```bash
PYTHONPATH=minimax python -m sddctx apply --env-file minimax/sddctx.env \
  --patch minimax/logs/minimax_patch.diff
```

**预期**：`applied: true`，`touched_files` 是
`minimax/workload/app/linewindow/reader.py`。应用后的文件与
`minimax/workload/snapshots/after/app/linewindow/reader.py` 逐字一致。

### 步骤 9：记录改动后的通过

```bash
python minimax/scripts/run_tests.py target-after
python minimax/scripts/run_tests.py regression
```

**预期**：两个命令退出码都是 0。目标测试 12 条全过，回归测试 22 条全过。

### 步骤 10：确认规格更新后模块使用新内容

```bash
python minimax/scripts/verify_spec_change.py
```

**预期**（日志 `minimax/logs/spec_change.log`）：

```
## before the specification change
revision: 1
contains_marker: False
digest: 207b405b4f8f5227

## after the specification change
revision: 2
contains_marker: True
digest: 0bd9d5ed07b3ac14

# result: passed
```

即：把规格换成 revision 2 并重新导入之后，下一次上下文里的规格版本号变成 2，
只有 revision 2 才有的「报告形式」一节出现在正文里，上下文摘要也发生变化。脚本
开始时会把业务工程退回改动前，结束时把规格还原成 revision 1、重新应用补丁并重新
导入，所以两次的摘要与本次任务上下文用的是同一个基线。

### 步骤 11（可选）：一次跑完全部

```bash
python minimax/scripts/run_verification.py
```

**预期**：退出码 0，`minimax/logs/verification.log` 里五个步骤的退出码依次是
`0`（退回）、`1`（改动前失败）、`0`（应用补丁）、`0`（改动后通过）、`0`（回归）。

## 六、重置方法

| 要重置什么 | 命令 |
| --- | --- |
| 业务工程代码回到改动前 | `python minimax/scripts/reset_workload.py --state before` |
| 业务工程代码回到改动后 | `python minimax/scripts/reset_workload.py --state after` |
| 规格回到 revision 1 | `python minimax/scripts/reset_workload.py --state before`（快照含 `specs/SPEC-001-read-range-clamp.md`） |
| 规格切到 revision 2 | 复制 `minimax/workload/snapshots/spec-v2/specs/SPEC-001-read-range-clamp.md` 到 `minimax/workload/specs/`，再执行 `sddctx init --reset` |
| seekdb 中的全部资料 | `PYTHONPATH=minimax python -m sddctx init --reset --env-file minimax/sddctx.env` |
| PowerContext 中的任务状态 | 删除 `minimax/data/powercontext.db` 后重启 Server，或换一个 `--task-id` |
| 全部测试日志 | 删除 `minimax/logs/` 下的 `*.log` |

`reset_workload.py` 只覆盖 `minimax/workload/app/` 与 `minimax/workload/specs/`
下与快照同名的文件，不会删除其他内容。
