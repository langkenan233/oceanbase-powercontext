# 技术说明（一页）

## 1. 方案

```
浏览器                                  本地 Node 进程              seekdb（嵌入式）
├─ 切分文本（句边界 + 重叠窗口）
├─ ONNX 推理：bge-small-zh-v1.5 ──┐
│   WebGPU/FP16 或 WASM/INT8      │
└─ 向量 + 原文 + 元数据 ──────────┴─→ 校验维度 → 批量写入 → refresh_index()
                                                              │
└─ 查询向量化 → 一次 hybridSearch ─────────────────────────────→ DBMS_HYBRID_SEARCH
                                                                 全文 query_string
                                                                 向量 KNN
                                                                 RRF 融合
   ←─────────────── 已排序的最终结果 ←────────────────────────────┘
```

浏览器只做两件事：切分与推理。检索请求到达服务端后只有一次数据库调用，排序结果原样返回，应用侧不取两路结果、不做二次合并。服务端对写入行做维度校验，本身不具备任何 embedding 能力。

## 2. 模型与量化

| 项目 | 取值 |
| --- | --- |
| 模型 | `BAAI/bge-small-zh-v1.5`，权重源 <https://huggingface.co/BAAI/bge-small-zh-v1.5> |
| ONNX 转换版 | `Xenova/bge-small-zh-v1.5`，经 hf-mirror 镜像获取 |
| 结构 | BERT 4 层，hidden 512，最大输入 512 token |
| 句向量 | CLS 位输出 + L2 归一化（与模型训练方式一致） |
| 运行时 | Transformers.js 3.8.1 + ONNX Runtime Web |

三种精度均为官方仓库提供的同结构权重，未做二次训练：

| 精度 | 文件 | 体积 | 相对 FP32 |
| --- | --- | --- | --- |
| FP32 | `onnx/model.onnx` | 90.4 MiB | 100% |
| FP16 | `onnx/model_fp16.onnx` | 45.3 MiB | 50.1% |
| INT8 | `onnx/model_quantized.onnx` | 22.9 MiB | 25.3% |

INT8 采用 ONNX Runtime 的静态量化方案（权重与激活按校准范围映射到 8 位整数），FP16 为权重与计算半精度化。

## 3. 检索质量

评测集：示例语料 41 篇，人工标注 25 条查询，其中 15 条为语义类（问法与原文用词不同），10 条为关键词类（含 `RRF`、`SharedArrayBuffer`、`ngram_token_size` 这类专有词）。指标为 recall@5 与 MRR，标注文档出现在前 5 位即算命中。

**量化前后（仅向量检索，隔离模型差异）**

| 精度 | recall@5 | MRR |
| --- | --- | --- |
| FP32 | 84% | 0.705 |
| FP16 | 84% | 0.725 |
| INT8 | 84% | 0.710 |

三种精度的 recall@5 相同，MRR 差异在 0.02 以内，量化在本语料上没有可测量的质量损失。

**混合检索的增益（同一索引，同一向量）**

| 检索方式 | 语义类 15 条 | 关键词类 10 条 | 总体 | MRR |
| --- | --- | --- | --- | --- |
| 仅向量 | 87% | 70–80% | 84% | 0.705 |
| 向量 + 全文 RRF | 80% | 90% | 84–88% | 0.691 |

关键词类是混合检索的价值所在：向量模型对 `RRF`、`COOP`、`ngram_token_size` 这类低频词不敏感，全文侧把它们精确命中，recall@5 从 70% 提到 90%。语义类略有下降，原因是整句作为 `query_string` 时按 OR 展开，命中的文档集合偏宽。缓解手段是 RRF 常数从 60 降到 2、候选窗口收到 10：早期顺序的命中权重远高于尾部，噪声项挤不进前列。下表是参数扫描结果。

| 配置 | 语义类 | 关键词类 | 总体 | MRR |
| --- | --- | --- | --- | --- |
| 仅向量 | 87% | 70% | 80% | 0.715 |
| rrf k=60 pool=40 | 80% | 80% | 80% | 0.664 |
| rrf k=10 pool=10 | 87% | 80% | 84% | 0.671 |
| rrf k=2 pool=10（采用） | 87% | 90% | 88% | 0.693 |
| rrf k=1 pool=10 | 87% | 90% | 88% | 0.687 |

## 4. 推理后端与降级

启动时检测 `navigator.gpu` 并尝试申请适配器，成功则用 WebGPU，失败或初始化异常则回落到 WASM，界面标签同步变更。地址栏加 `?device=wasm` 可强制降级。

后端与精度必须按对匹配，这一点由实测确定（同一段文本编码两次的余弦、与无关文本的余弦）：

| 后端 | 精度 | 自身相似度 | 无关文本相似度 | 结论 |
| --- | --- | --- | --- | --- |
| WebGPU | INT8 | 0.671 | 0.751 | 不可用，向量已失真 |
| WebGPU | FP16 | 1.000 | 0.497 | 可用 |
| WASM | INT8 | 1.000 | 0.507 | 可用 |
| WASM | FP32 | 1.000 | 0.498 | 可用 |

INT8 图在 WebGPU 上算出的向量与模型真实输出无关，且能通过推理不报错，只有做数值比对才会暴露。因此 INT8 只在 CPU 上启用，WebGPU 固定 FP16。

## 5. 性能实测

**批大小与吞吐**（32 段等长文本，单位：总耗时 / 每秒条数）

| 批大小 | WebGPU · FP16 | WASM · INT8 |
| --- | --- | --- |
| 1 | 211 ms / 151.5 | 895 ms / 35.7 |
| 4 | 58 ms / 553.0 | 361 ms / 88.8 |
| 8 | 36 ms / 883.0 | 332 ms / 96.4 |
| 16 | 32 ms / 1011.5 | 326 ms / 98.2 |
| 32 | 30 ms / 1066.1 | 334 ms / 95.8 |

WebGPU 在批大小 16 之后基本饱和，从批 1 到批 32 提升 7.0 倍；WASM 在批 16 饱和，提升 2.7 倍。默认批大小取 8（吞吐已达峰值的 85% 以上，同时保持导入进度可见），导入区可手动调整。

**端到端耗时**（41 段语料，WebGPU · FP16）

| 阶段 | 耗时 |
| --- | --- |
| 模型加载 + 预热 | 0.83 s |
| 41 段向量化 | 0.19–0.46 s（89–211 段/秒，取决于内核是否已预热） |
| 写入 seekdb | 181 ms |
| 索引刷新 `refresh_index()` | 516 ms |
| 单次混合检索（库内部分） | 5–28 ms |
| 查询文本向量化 | 13–21 ms |

已做的优化：页面初始化后立即用一段文本预热，把内核编译成本从用户首次查询里移走；写入按批提交后再统一刷新一次索引，避免逐条刷新；静态资源与模型文件带一年期不可变缓存；服务端返回跨源隔离响应头，使 WASM 后端可以使用多线程。

## 6. seekdb 的使用

- 集合配置：`hnsw{ dimension=512, distance=cosine }`，全文分析器 `ik(smart)`，维度由应用声明，不依赖远端 embedding。
- 写入：用 `upsert()` 批量提交向量、原文与元数据（标题、来源、片段序号）。主键由「来源文件名」哈希加片段序号生成，写入前先按 `docId` 删除该来源的旧片段，因此重复导入是替换而非追加，文件改短后多余片段也不会残留。
- 刷新：每次导入结束调用 `refresh_index()` 并记录耗时，返回后再提示导入完成，保证新增内容立即可查。
- 检索：`hybridSearch()` 把全文查询与查询向量写进同一份搜索参数，由 `DBMS_HYBRID_SEARCH.GET_SQL` 生成 SQL 并在库内执行，返回 RRF 融合后的排序。

## 7. 已知限制

- 评测集只有 41 篇文档、25 条查询，recall 的分辨率是 4 个百分点，只能说明量级，不足以做强结论。
- 两条查询稳定未命中：`怎么让模型变小` 未能通过「量化」命中，`长文档切太碎怎么办` 落在「长文档为什么要切分」而非「重叠窗口的作用」。属于小参数量模型的语义泛化边界，词表扩展或换更大模型可解，但会牺牲端侧体积。
- 整句作为全文查询时按 OR 展开，纯中文自然问句的全文侧噪声偏大，混合检索在这类查询上低于纯向量。
- 仅在 Windows 11 + Edge（Intel 核显）上验证过 WebGPU 路径；其它 GPU 厂商未经测试。
- 图片内容未支持，扩展方向见语料中的说明。
